# 結合生成式人工智慧與地理資訊之智慧旅遊行程規劃系統

## 畢業專題指導建議

整理日期：2026 年 10 月 15 日  
適用對象：資訊工程相關科系畢業專題團隊

## 一、整體評估與研究定位

本題適合作為資工系畢業專題，能整合網站開發、資料庫、地圖應用、生成式 AI 與演算法，也有研究比較與成果展示的空間。

**核心應放在「行程是否可執行」，而不只是讓 AI 產生旅遊介紹。** 系統應能回答：景點是否真實、抵達時是否營業、移動時間是否合理，以及當日是否玩得完。

建議第一階段目標：

> 完成一套以臺南一日遊為範圍，能理解自然語言需求，依據真實景點資料與交通時間，產生可檢查、可修改之個人化行程的網頁系統。

## 二、題目名稱與範圍收斂

原題目可以保留，但建議增加研究範圍：

> 結合生成式人工智慧與地理資訊之個人化旅遊行程規劃系統——以臺南市為例

若希望凸顯技術重點，可使用：

> 結合生成式人工智慧與時空限制之個人化旅遊行程規劃系統

「時空限制」是同時考量景點位置、營業時間、移動時間與每日可用時間。

| 項目 | 建議範圍 |
| --- | --- |
| 地區 | 臺南市 |
| 天數 | 先完成一日遊，再擴充兩日遊 |
| 交通 | 先支援一種，例如開車 |
| 資料 | 約 50～100 筆經過整理的景點與餐飲資料 |
| 平台 | 支援手機瀏覽的網頁系統 |

範圍較小有利於提升資料與規劃品質，也容易設計一致的測試情境。

## 三、研究問題與研究價值

| 研究問題 | 白話說明 | 可驗證成果 |
| --- | --- | --- |
| 如何將自然語言轉成旅遊條件？ | 理解「不要太累、喜歡室內」等描述 | 條件擷取正確率 |
| 如何產生符合時間與地理限制的行程？ | 避免景點太遠、抵達時已關門 | 可行行程比例、交通時間 |
| 如何在修改需求後重新規劃？ | 刪除景點後，其他安排仍合理 | 重排成功率、回應時間 |

**研究價值在於驗證：加入地理資料與限制檢查後，是否比直接請 AI 排行程更可靠。**

「提高滿意度」「縮短交通時間」應先列為研究目標，待實驗完成後才能寫成研究成果。

## 四、系統架構與 AI 分工

### 4.1 核心原則

> AI 理解需求並解釋行程；資料庫提供事實；規劃程式負責計算與檢查。

### 4.2 使用情境

使用者輸入：

> 幫我排臺南一日遊，早上十點出發，晚上七點結束，喜歡美食和室內景點，兩人預算兩千元，不要走太多路。

系統轉換為明確條件：

| 欄位 | 擷取結果 |
| --- | --- |
| 地區 | 臺南 |
| 時間 | 10:00～19:00 |
| 人數 | 2 人 |
| 總預算 | 2,000 元 |
| 偏好 | 美食、室內 |
| 步行需求 | 需進一步量化或提供選項 |
| 交通方式 | 尚未提供，應詢問 |

「不要走太多路」尚不足以直接計算，可讓使用者選擇「每段步行不超過 10 分鐘」等具體條件。系統也應確認出發地點與必要的終點條件。

### 4.3 建議處理流程

1. AI 擷取使用者需求。
2. 確認缺漏與模糊條件。
3. 從資料庫篩選符合條件的候選景點。
4. 取得候選景點之間的交通時間。
5. 程式安排順序、停留時間與用餐時間。
6. 檢查營業時間、預算與當日結束時間。
7. AI 將通過檢查的結果轉成易讀說明。
8. 使用者修改需求後，重新規劃並再次驗證。

可使用結構化輸出，讓模型依指定欄位回傳資料，方便後端處理；但格式正確不代表內容正確，後端仍須驗證。[1]

**不要讓模型自行編造景點、票價、營業時間或交通分鐘數。**

## 五、地理資訊的實際應用

只有地圖標記會使地理資訊的應用偏薄弱，建議讓地理資料參與實際規劃。

| 地理功能 | 實際用途 |
| --- | --- |
| 鄰近景點查詢 | 找出指定位置周邊的候選景點 |
| 景點區域分組 | 減少跨區來回 |
| 道路交通時間計算 | 判斷是否來得及抵達下一站 |
| 路線與順序顯示 | 讓使用者看懂移動安排 |
| 刪除景點後重新排序 | 維持剩餘行程的合理性 |

資料量較小時，可先用座標距離篩選候選景點；正式排程應使用道路路線估計時間。直線距離無法反映繞路、單行道或不同交通方式。

若採 PostgreSQL 搭配 PostGIS，可使用 `ST_DWithin` 進行指定距離內的空間篩選，並注意座標系統與距離單位。[2]

## 六、行程規劃演算法

### 6.1 第一版策略

不必一開始自行訓練模型，也不必同時加入多種最佳化演算法。建議先採容易說明與驗證的方式：

1. 依使用者偏好替景點評分。
2. 篩除時間或預算不符的景點。
3. 依交通時間安排順序。
4. 超時時移除較低優先的景點。
5. 再次檢查整份行程。

完成後，再考慮使用 OR-Tools 等工具處理時間窗限制。官方已有結合交通時間與允許到訪時段的路線規劃範例，可作為實作參考。[3]

旅遊規劃還包含「哪些景點值得選」，不能只套用最短路線。須說明景點選擇、順序安排與兩者之間的取捨。

### 6.2 硬性限制與軟性偏好

| 類型 | 例子 | 系統處理方式 |
| --- | --- | --- |
| 硬性限制 | 必須在 19:00 前結束、必去景點 | 原則上不可違反 |
| 軟性偏好 | 喜歡室內、希望少移動 | 盡量滿足，並說明取捨 |

若條件衝突，應說明原因，讓使用者選擇放寬哪項條件；不可硬排一份無法執行的行程。

若無法證明全域最佳，成果應稱為「符合限制的推薦行程」，避免直接宣稱「最佳行程」。

## 七、功能優先順序

| 優先程度 | 建議功能 |
| --- | --- |
| 必做 | 自然語言輸入、條件確認、景點資料庫、行程生成 |
| 必做 | 地圖標記、交通時間、營業時間檢查 |
| 必做 | 刪除或替換景點後重新規劃 |
| 加分 | 推薦原因、資料來源與更新日期 |
| 加分 | 雨天替代行程、儲存與分享行程 |
| 後續擴充 | 多日旅遊、大眾運輸、多人偏好協調 |

飯店訂房、機票比價、付款、社群與全臺景點支援，建議暫時不納入第一版，以免排擠核心規劃功能的開發與驗證時間。

## 八、資料品質與景點欄位

每個景點至少包含：

| 欄位 | 說明 |
| --- | --- |
| 景點編號 | 作為模型引用與後端驗證的依據 |
| 名稱、地址、經緯度 | 確認景點身分與位置 |
| 景點分類 | 例如文化、美食、自然景觀 |
| 室內／室外屬性 | 支援偏好與替代方案 |
| 建議停留時間 | 標示為估計值 |
| 預估費用 | 說明計算單位與包含項目 |
| 每週營業時間、休息日 | 支援到訪時間檢查 |
| 資料來源、最後更新日期 | 支援追溯與維護 |

營業時間可能臨時變更；資料未知時應標記「待確認」，不可把缺少資料當作全天開放。建議先完成小而可靠的資料集，再逐步擴充。

## 九、實驗設計與成果驗證

### 9.1 比較組別

| 版本 | 做法 | 比較目的 |
| --- | --- | --- |
| A | 直接請生成式 AI 排行程 | 作為基準 |
| B | AI 搭配相同景點資料 | 觀察資料支援的影響 |
| C | AI＋景點資料＋地理與時間限制檢查 | 觀察規劃機制的影響 |

三組盡量使用相同模型、需求與輸出要求，記錄模型版本與測試日期。由於生成結果具有變動性，適合對相同情境重複測試。

### 9.2 評估指標

| 指標 | 衡量內容 |
| --- | --- |
| 條件擷取正確率 | 自然語言轉換成欄位的正確程度 |
| 景點資料正確率 | 是否出現不存在或資料錯誤的景點 |
| 營業時間違規率 | 抵達與完整停留是否落在開放時段 |
| 行程可行率 | 是否符合所有硬性限制 |
| 總交通時間 | 在可行條件下是否減少移動 |
| 偏好符合度 | 景點是否符合使用者需求 |
| 回應時間與成本 | 生成一次行程所需時間與費用 |

**不能只比較交通時間。** 少排景點也可能降低交通時間，因此須同時比較景點數量、偏好符合度與停留品質。

### 9.3 測試情境

可先設計 20～30 組固定情境，涵蓋：

- 親子旅遊。
- 室內景點偏好。
- 美食主題。
- 低預算。
- 指定必去景點。
- 景點休息或營業時段受限。
- 刪除景點後重新安排。
- 條件無法同時滿足。

再搭配小規模使用者測試；受試者不多時，應將結果定位為初步評估。上述數量為規劃建議，不代表已完成實驗。

## 十、口試準備

| 教授可能提問 | 回答重點 |
| --- | --- |
| 和直接問 ChatGPT 有什麼不同？ | 有可追溯資料、道路時間計算及限制驗證，並以實驗比較 |
| 地理資訊用在哪裡？ | 候選篩選、交通時間、路線排序與重新規劃 |
| 團隊自己做了什麼？ | 資料整理、需求轉換、排程規則、驗證機制及系統整合 |
| AI 編造資料怎麼辦？ | 只接受資料庫中的景點編號，後端檢查所有引用 |
| 為什麼稱為最佳行程？ | 若無法證明全域最佳，改稱符合限制的推薦行程 |
| API 無法使用怎麼辦？ | 顯示錯誤與資料狀態，展示時備妥清楚標示的測試資料 |

## 十一、指導建議結語

第一版應優先做好「理解需求、可靠資料、可行排程、修改重排、實驗驗證」五件事。

真正值得投入的亮點，是讓使用者看得出來：**系統為什麼這樣排，以及這份行程為什麼做得到。**
